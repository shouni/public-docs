# ライブラリリファレンス

Go で GCP・AI モデル・各種ストレージをつなぐ公開ライブラリ群について、**各ライブラリの担当範囲と、そう決めた理由**を引くための資料です。

使い方・API・オプションは各リポジトリの README と godoc にあります。ここにあるのは境界の引き方だけです。
層の下から順に並んでいます。全体の設計思想と層の関係は「[個人開発エコシステムの全体像](https://zenn.dev/snknsk/articles/shouni-go-ecosystem-overview)」を参照してください。
アプリケーションと MCP サーバーは [applications.md](applications.md) にあります。

## 🏗️ コア基盤ライブラリ群 (Core Infrastructure Libraries)

インフラストラクチャとの接続、通信の安全性、リトライ制御、ストレージアクセス、素材の取得、音声バイナリの操作、結果の通知を抽象化する基盤ライブラリと、その上に乗る非同期ジョブの共通基盤です。いずれもAIの話を一切含まないため、生成系以外のアプリケーションでもそのまま使えます。

### netarmor

エコシステムで**最も広く行き渡っている**ライブラリです。`go.mod`にこのモジュールが現れるリポジトリは12あり、そのうち直接requireしているのは7で、残りは`go-http-kit`を経由して入ってきます。外部通信の「安全性」だけを担当し、AIもクラウドサービスも知りません。

**このモジュールは外部依存を持ちません。** `go.mod`の`require`は空で、`go.sum`も0バイトです。これだけの数のリポジトリが取り込む土台なので、ここに1行足すと使わないリポジトリのモジュールグラフにまで載ります。指数バックオフの`retry`パッケージは、当初ここに同居していました。使っているのが`go-http-kit`と、元からそれに依存していた`go-web-reader`だけだったので、**そちらへ移しています**。依存辺は1本も増えず、代わりに`require`が空になりました。

* **接続の直前にIPを検証する**: URLを検証してから接続するまでの間に、DNSの解決結果が差し替わる余地が残ります（DNS Rebinding / TOCTOU）。`NewSafeTransport`はTransport層で**接続の直前に名前解決を行い、検証済みのIPへ直接接続**することでこの隙間を塞ぎます。環境変数の`HTTP_PROXY` / `HTTPS_PROXY`を使わないのも同じ理由で、プロキシを挟むと「検証したIPへ繋ぐ」が成立しなくなるためです。
* **許可するスキームは`http`と`https`だけ**: 以前は`gs://`や`s3://`も「名前解決せず通す」対象でしたが、v1.3.0で落としました。**接続しないURIを検証器が通すと、検証を通った事実が何も保証しなくなる**ためです。クラウドストレージのスキーム判定は、実際に読み書きする`go-remote-io`側の仕事に寄せました。
* **失敗理由は型で分類する**: すべて`errors.Is` / `errors.As`で判別でき、エラーメッセージの文字列比較が要りません。リゾルバを差し替えられるので、実DNSに依存しないテストも書けます。

**最下層に置いている理由**は、SSRF対策が「どのライブラリでも同じ書き方をしたい」ものであり、かつ**間違えても動いてしまう**部類だからです。プライベートIPへの接続を1か所で塞ぎ忘れても、通常の利用では何も起きません。

このライブラリだけを、セキュリティ / アジリティ / レジリエンス / トレーサビリティの4つの柱という切り口で書いた記事があります：[AIのカオスに対抗する、NetArmor「凡事徹底」の4つの柱と設計哲学](https://zenn.dev/snknsk/articles/netarmor-four-pillars)（執筆時点では`retry`も同居していました）。

[GitHub - shouni/netarmor](https://github.com/shouni/netarmor)

### go-utils

複数のプロジェクトで実際に重複していた小さな処理だけを集めたモジュールです。`jobid`（ジョブIDの採番・検証）、`jst`（日本標準時への変換）、`slogctx`（contextに積んだ属性を自動で付けるslogハンドラ）、`strlist`（設定値の文字列リスト正規化）の4パッケージが、互いに独立して入っています。

`utils`という名前は何でも受け入れてしまうため、**収録の可否を3つの条件で決めています**。

* **外部依存を持たない**: 標準ライブラリだけで完結すること。実際、このモジュールの`go.mod`に`require`は1行もありません。
* **I/Oやインフラに触れない**: ネットワークやクラウドSDKを扱うものは`go-remote-io`や`gcp-kit`など目的別のライブラリの担当です。
* **2つ以上のプロジェクトから使われている**: 1つでしか使わないものは、その利用者側の`internal/`に置きます。汎用に見えて、実際にはそのプロジェクト固有の判断に紐づいていることが多いためです。

3つ目の条件が効いていて、この4パッケージは現在9リポジトリから直接importされています。基盤ライブラリの`gcp-kit` / `go-job-kit` / `go-notify`もここに依存しますが、逆向きの依存はありません。

[GitHub - shouni/go-utils](https://github.com/shouni/go-utils)

### go-serve-kit

HTTP サービスが**応答を返す側**で毎回書くことになる定型——防御的ヘッダー、表現の出し分け、役割の宣言——だけを引き受けます。サーバーそのものは持ちません。`respond` / `secureheaders` / `serverrole` の3パッケージが互いに独立して入っており、**`go.mod`の`require`は空です**。

元は`gcp-kit`に同居していましたが、いずれもGCPに依存しない処理だったため切り出しました。クラウドを使わないHTTPサービスがCloud Run向けのキットごと取り込む形になっていたためで、`gcp-kit`との間に依存はありません。

* **表現の選択と `Vary: Accept` を切り離さない**: `respond.WantsJSON` は `ResponseWriter` を受け取り、判定と同時に `Vary: Accept` を立てます。同じ URL が `Accept` で中身を変えるのにキャッシュへ伝えないと、CDN を挟んだとき JSON を求めたクライアントへ HTML が返りえます。**5つの兄弟アプリがこの1行を写し取っていて、5つとも `Vary` を落としていました**。判定に `w` を要求すれば、宣言だけ忘れることが構造的に起きません。判定は `Accept` に `application/json` が含まれるかだけを見ます。q値まで解釈しないのは、利用側がいずれも明示的に `Accept` を送っているためです。
* **役割の未設定を `both` に丸めない**: `serverrole` は `web` / `worker` / `both` の語彙と `Parse` だけを持ち、**未設定と未知の値はどちらもエラーにします**。未設定を`both`に落とすと、環境変数が1つ欠けただけで公開側にworkerのルートが復活します。未知の値を黙って受け入れると、今度は何のルートも提供しないサービスがデプロイされます。どちらも起動時に落とすほうが安全です。
* **ヘッダーの既定は「何も許可しない」**: `secureheaders` の既定は外部オリジンを1つも許可せず、インラインスタイルも許しません。第三者製のJS/CSSをCDNではなく自前配信している前提で、足りない分だけ設定で開けます。**既定値は、兄弟アプリが1バイト違わず同じものを持っていた**ところから起こしています。

[GitHub - shouni/go-serve-kit](https://github.com/shouni/go-serve-kit)

### gcp-kit

Cloud Run 上のWebアプリと、Cloud Tasksで動く非同期ワーカーが毎回同じように書くことになる部分——ログイン、セッション、タスクの投入と受信、ログの体裁——だけを引き受けます。5つのパッケージ（`auth` / `cloudlog` / `cloudrun` / `tasks` / `worker`）は独立していて、必要なものだけをimportできます。

* **認証は「契約」と「実装」に分かれている**: `auth` が持つのは `Authenticator`（`Authenticate(w, r)`）という契約と、
  それを組み合わせる `Require` / `Protected` だけで、標準ライブラリしか使いません。実装は人向けの `auth/session`
  （OAuth2 + セッション + CSRF）とサービス向けの `auth/oidc`（受信 Bearer の検証）に分かれ、依存は
  `session → auth ← oidc` の一方向です。**同じルートに人とエージェントが来る**構成を1か所で表現するための形で、
  各アプリが同じ合成を手で書くと、認証経路が散らばって片方だけ強化される事故が起きます。
* **「試していない」と「設定されていない」を別のエラーにする**: 前者（`ErrNotAttempted`）は「自分の担当ではない」で
  次の方式へ静かに譲り、後者（`ErrNotConfigured`）は設定ミスです。**混ぜると設定漏れがフォールバックに隠れ**、
  「なぜかエージェントだけログイン画面に飛ばされる」という分かりにくい形で現れます。
* **応答を決めるのは、資格情報を提示したうえで落ちた方式**: Bearer を出して通らなかったエージェントは
  RFC 6750 に沿って 401 `invalid_token`（取り直せば直る）か 403 `insufficient_scope`（取り直しても直らない）を
  受け取り、何も出していないブラウザはログイン画面へ送られます。**最後の方式に答えさせると、JSON を求めた
  エージェントに HTML のログイン画面が返ります**。
* **audience だけでは呼び出し元を絞れない**: 受信したOIDCトークンは、署名とaudienceに加えて**サービスアカウントの許可リスト**まで照合します。audienceは誰でも指定できる文字列に過ぎず、それだけでは「このURLを知っている誰か」までしか絞れないためです。
* **設定漏れは起動時に落とす**: 検証器は`Configured()`を持ちます。**OIDCの設定漏れにリクエスト時まで気づかないと、Cloud Tasksがリトライを重ねた末にタスクを破棄します**。起動時に落としたほうが、失敗が1回で済みます。
* **`DispatchDeadline` はワーカーの実効上限**: 未指定だとCloud Tasksの既定10分が上限になり、Cloud Runの`timeout`をいくら伸ばしても超えられません。**アプリ側の全体タイムアウトはこれより短く**取ります。でないと、失敗を記録する前にcontextごと打ち切られます。
* **ログの体裁だけを直し、出力先とレベルは持たない**: `cloudlog`はslog既定の`level`/`msg`を`severity`/`message`へ詰め替えます。これが無いとLogs Explorerで全エントリがINFO扱いになるためです。逆に、どこへ出すか・どのレベルから出すかはGCPに依存しないので、意図的にアプリケーション側へ残しています。
* **タスクの型が、投入側と受信側の契約になる**: `tasks`と`worker`がGenericsの`T`を共有するため、投入時のシリアライズと受信時のデコードが同じ型に紐づきます。決定的な名前での投入（`ALREADY_EXISTS`は成功扱い）、`worker.ErrPermanent`による打ち切り、再試行回数の参照が揃っているので、冪等に書けます。

このキットが前提にしている Cloud Run 側の構成は、3本に分けて書いています。

* 1つのイメージを web / worker の2サービスに分け、役割で依存グラフを切り替える：[Cloud Run で 1 つのイメージを web/worker に分け、権限と設定を絞る](https://zenn.dev/snknsk/articles/cloudrun-web-worker-split)
* `tasks` / `worker` に相当する非同期処理を、Go と Python で並べた比較：[Cloud Run + Cloud Tasks の非同期処理を Go と Python で比較する](https://zenn.dev/snknsk/articles/cloudrun-cloudtasks-go-python)
* 環境変数やモデル名をアプリのビルドから切り離す：[モデル名を変えるたびに、アプリをフルビルドしていた。Cloud Run の設定を Terraform へ移す](https://zenn.dev/snknsk/articles/cloudrun-config-terraform-import)

[GitHub - shouni/gcp-kit](https://github.com/shouni/gcp-kit)

### go-http-kit

`netarmor/securenet`によるSSRF対策と指数バックオフを最初から組み込んだ`net/http`互換のHTTPクライアント（`httpkit.New`）と、その土台になる汎用リトライ（`retry`）の2パッケージです。`Doer`インターフェースを受け取るので、既存の`*http.Client`やテスト用のモックをそのまま差し込めます。

* **役割を2つに割る**: `retry`は「いつ・どれだけ待つか」だけを決め、「何を再試行する価値があるか」と「リクエストをどう再送するか」は`httpkit`が持ちます。HTTPの知識を`retry`側へ漏らさないための線引きです。この分離があるので、HTTPを介さない`go-web-reader`の取得ループも同じエンジンに乗れます。
* **リトライの対象を絞る**: 再試行するのは5xxと、4xxのうち408・429だけです。サーバーが`Retry-After`を返した場合は、バックオフの算出値の代わりにその待機時間を使います。**それ以外の4xxは`NonRetryableHTTPError`として即座に返します**。認証エラーや不正なリクエストは何度投げ直しても結果が変わらないためです。
* **リトライ判定はHTTPメソッドを見ない（意図的）**: 判定関数は`error`だけを受け取るため、GETもPOSTも同じ扱いです。つまり**非冪等な送信は二重実行になり得ます**。5xxや読み取りタイムアウトは「サーバーに届いていない」ことを保証せず、届いた上でレスポンスを取りこぼしただけなら、再送で同じ副作用がもう一度起きます。それでもメソッドで自動判定しないのは、**冪等性が「操作」の性質であって「メソッド」の性質ではない**ためです（副作用のないPOSTも、再送したくないDELETEも実在します）。Go標準の`net/http`もgRPCもAWS SDKも明示宣言を採っており、ここでは`WithoutRetry`で派生させたクライアントがその宣言にあたります。設定とコネクションプールは共有されるので、クライアントを2つ組み立てる必要はありません。
* **URLの事前検証はリトライ実行部の1箇所だけに置く**: ヘルパー経由でも、自前で組み立てた`*http.Request`を渡しても、検証は同じ場所を通ります。経路ごとに書くと、いずれか1本で必ず書き忘れます。
* **ストリームは全体タイムアウトから外す**: 大きなファイルの取得がリクエスト単位のタイムアウトで途中終了しないよう、専用のクライアントで実行します（コネクションプールは共有）。読み込み量は`MaxResponseBodySize`（既定25MB）で打ち切ります。

[GitHub - shouni/go-http-kit](https://github.com/shouni/go-http-kit)

### go-remote-io

Google Cloud Storage・Amazon S3・ローカルファイルシステムを、URIスキームの自動判定で`Open(ctx, path)`一本に揃えるI/Oライブラリです。

* **抽象が成立する条件は、エラーの意味を揃えること**: 「見つからない」はスキームを問わず`os.ErrNotExist`を包んで返す、`Exists`の不在は`(false, nil)`でエラーにしない、`Delete`は対象が無くても`nil`を返して冪等にする——ここを揃えないと、呼び出し側は結局保存先ごとに分岐します。**インターフェースの形だけ統一しても、抽象にはなりません**。
* **「URIが不正」を「対象が無い」に混ぜない**: `gs://bucket`のようにオブジェクト名が空のURIはエラーにします。バケット操作との取り違えを防ぐためで、未登録スキームも「未対応」と明示して返します。設定漏れと非対応を区別できます。
* **コアはクラウドSDKをimportしない**: 本体は抽象だけを持ち、GCS SDKは`gcs`、AWS SDKは`s3`パッケージだけが依存します。片方しか使わないアプリのビルドに、もう片方のSDKが入りません。
* **一覧の区切り文字**: `List`に`WithDelimiter("/")`を渡すとプレフィックス直下だけが対象になり、その先は「疑似ディレクトリ」として畳まれます。**これが無いと配下の全オブジェクトが返るため、1ジョブに成果物が数十あれば同じ数だけ受け取って呼び出し側で潰すことになります**。走査をサーバー側へ寄せるための口です。
* **署名付きURLと書き込みオプション**: 期限付きの署名付きURLを発行でき、書き込み時は`Content-Type` / `Content-Disposition` / `Cache-Control`を型安全に指定できます。ブラウザでのインライン再生と強制ダウンロードを出し分けられます。

このライブラリが書き出す先の設計——成果物とメタデータを分けて置く、署名付きURLで配信する、削除で関連オブジェクトをまとめて消す——は「[AIアプリの成果物を履歴・再生・削除まで扱う設計](https://zenn.dev/snknsk/articles/gcs_object_design)」にまとめています。

[GitHub - shouni/go-remote-io](https://github.com/shouni/go-remote-io)

### go-web-reader

`https://` / `gs://` / `s3://` を同じ `Open(ctx, uri)` で読むライブラリです。**AIに渡す素材を取ってくる側**を担当します。

go-remote-io と役割が紛らわしいので、線引きを明示しておきます。両方 `gs://` を読みますが、担当している工程が違います。

| | go-remote-io | go-web-reader |
| --- | --- | --- |
| 方向 | 読み書き両方（+ 署名付きURL・一覧） | **読み取り専用** |
| 対象 | `gs://` / `s3://` / ローカル | `https://` / `gs://` / `s3://`（**ローカルは非対応**） |
| 立ち位置 | **成果物の置き場** | **素材の取得元** |
| HTML | バイト列としてそのまま | **本文だけを抽出**（広告・ナビゲーションを除去） |

* **Content-Typeによる自動切り替え**: HTMLは本文抽出、テキストや画像はそのまま返却、それ以外はエラーにします。呼び出し側がURLの中身を事前に知っている必要がありません。
* **接続直前にもIPを検証する**: ユーザーが入力したURLを叩く以上、取得前のURI検証だけでは足りません。検証を通ったあとにDNSが内部IPへ解決される経路を塞ぎます（`netarmor`の担当です）。
* **スキームごとの遅延初期化**: GCS/S3クライアントは対象スキームの初回`Open`時にだけ生成されます。ロックもスキームごとに独立しているため、GCSの初期化が詰まってもS3の呼び出しは待たされません。

[GitHub - shouni/go-web-reader](https://github.com/shouni/go-web-reader)

### audio

音声バイナリと日本語の読みだけを扱うライブラリです。netarmorと同じく、AIもクラウドも知りません。

* **デコードせずに結合する**: WAVをバイナリレベルで直接連結するため、再エンコードによる世代損失が起きません。RIFF/WAVE構造を解析して`fmt`と`data`チャンクを特定し、フォーマット不一致・4GB超過・壊れたヘッダーは結合前に弾きます。
* **読みを固定してから音声エンジンへ渡す**: 形態素解析（Kagome）で読みを補完しつつ、埋め込み辞書で表層形ごとの読みを上書きします。固有名詞や造語は解析器に任せると読みが安定しないため、**辞書で固定できるものは固定し、残りだけを解析器に任せる**という分担です。

読み正規化の実装は「[AIの誤読を許さない。プロンプトを安全な「読み形式」へトランスパイルする防衛戦術](https://zenn.dev/snknsk/articles/go-kagome-prompt-defense)」で1本にしています。

[GitHub - shouni/audio](https://github.com/shouni/audio)

### go-job-kit

Cloud Tasksへ投入し、オブジェクトストレージへ成果物を書き出す非同期ジョブの共通基盤です。**成果物が音楽であれ動画であれ漫画であれ、「投入する → 進行状況を記録する → 履歴をページングする」の骨格は同じ**になります。各アプリの`internal/`に同じ実装を抱えると少しずつ食い違っていくため、その共通部分だけを抜き出しました。

* **状態は成果物と別のファイルに記録する**: `queued` / `running` / `succeeded` / `failed` をストレージ上のJSONとして持ちます。**成果物は成功したジョブにしか存在しない**ため、そこに状態を相乗りさせると、生成中や失敗したジョブが履歴から消えてしまうからです。
* **「無い」と「読めなかった」を分ける**: `ErrNotFound`と`ErrUnavailable`を別のセンチネルエラーにしています。記録が無いなら処理を進めてよい一方、**読めなかっただけを「無い」とみなすと、完了済みのジョブを未完了と誤認して生成をまるごとやり直します**。判断が正反対になるため型で分けています。
* **at-least-once への再実行ガード**: Cloud Tasksは同じタスクを複数回配信し得ます。`Recorder.AlreadySucceeded`が記録済みの成功を根拠に二重実行を打ち切ります。
* **一覧は並行に読み、順序は保つ**: 履歴の1ページは数十回のストレージ読み取りになるため直列にできず、並行にすると順序が崩れます。`LoadPage`が既定10並列で読みつつ入力順を保ち、1件の破損でページ全体を失わせません。ただし`ctx`のキャンセルだけはエラーとして返します。読み込みが軒並み失敗した結果の「0件」を、正常な空一覧と区別できなくなるためです。
* **キャッシュのTTLは短く倒す**: メタデータ本体（既定10分）とジョブID一覧（既定1分）の2層です。後者が無いと履歴画面を開くたびにプレフィックス配下全体のlistが走ります。TTLを大幅に短くしているのは、新しく完成したジョブが一覧に現れるまでの遅延を抑えるためです。
* **成果物のドメインには踏み込まない**: 何を生成するかはアプリ側の関心で、共通なのは「状態をどう記録し、履歴としてどう見せるか」だけ、という線引きです。

履歴一覧の並列取得やキャッシュ、`job_id`の付け方といった運用側の判断は「[AIアプリの成果物を履歴・再生・削除まで扱う設計](https://zenn.dev/snknsk/articles/gcs_object_design)」で扱っています。

[GitHub - shouni/go-job-kit](https://github.com/shouni/go-job-kit)

### go-notify

非同期パイプラインの実行結果を人へ届ける部分だけを担当します。CLIを持たず、アプリケーションに組み込んで使います。

* **チャネル非依存の本文組み立て**: `notify.Body`は標準的なMarkdownを出力し、Slack固有のmrkdwn記法への変換は`slack`パッケージが担当します。**本文を組み立てるコードはチャネルを意識しません**。各メソッドは値が空なら何も書き込まないので、「この項目があれば書く」という`if`を項目の数だけ並べずに済みます。

## 🤖 AI抽象化ライブラリ群 (AI Abstraction Libraries)

LLM（Gemini等）のプロンプト構築、レスポンス管理、キャラクター定義の共有、および画像・音声・動画生成を抽象化するライブラリ群です。上位のオーケストレーターはこの層より下のSDKを直接importしません。

### go-prompt-kit

AIへのプロンプト管理と、レスポンスのドキュメント化（Markdown / JSON から HTML へ）を担当します。パッケージは4つで、`prompts`（テンプレート）・`resource`（`embed.FS`からの読み込み）・`frontmatter`（先頭メタデータの切り離し）・`htmldoc`（HTML化）が独立して入っています。

* **モードの説明はプロンプト自身に持たせる**: 何をするモードかをファイル先頭のfront matterに書いておくと、モードを増やす作業が「ファイルを1つ置く」だけで済みます。`frontmatter`はそれを本文から切り離し、AIへの指示の先頭にYAMLが紛れ込むのを防ぎます。
* **メタデータの書式は解釈しない**: 解析関数（`func(data []byte, v any) error`）を呼び出し側から受け取るため、このモジュールはYAMLライブラリに依存しません。ライブラリが解析器を固定すると、乗り換えのたびに利用側とリリースを揃える必要が生じます。実際`gopkg.in/yaml.v3`がアーカイブされ利用側が後継へ移ったとき、**このモジュールは1行も変えずに済みました**。
* **出力形式を変えても、CSSとレイアウトは変わらない**: `Converter`（本文をHTMLフラグメントに）・`Renderer`（CSS込みで包む）・`Document`（束ねる）の3段で、Markdownと構造化出力(JSON)は入口の`Converter`だけが入れ替わります。JSON側はスキーマを知らず、呼び出し側が渡した`html/template`にパース済みJSONを流すだけです。**「JSONで答えさせたい」が、ドキュメント生成の作り直しを意味しなくなります**。

4つのパッケージを入力から出力まで一本に並べて書いたのが「[モードを増やす作業を、Markdown 1枚に閉じ込める：Go でプロンプトをコードから引き剥がす](https://zenn.dev/snknsk/articles/go-prompt-kit-mode-per-file)」です。設計判断の背景はそちらで実コードとともに扱っています。

[GitHub - shouni/go-prompt-kit](https://github.com/shouni/go-prompt-kit)

### go-gemini-client

Google Gemini API / Vertex AI向けのデュアルバックエンド対応クライアントです。API Key方式（Google AI Studio）とProject ID / Location ID方式（Vertex AI）を1つのクライアントで切り替えられます。エコシステム内のGemini / Vertex AI 呼び出しは、すべてこのライブラリを経由します。

* **SDKの乗り換えで書き換わる範囲を、このモジュールに閉じる**: 上位が依存するのは`Generator`（`GenerateWithAttachments`の1メソッド）だけです。構造化出力・安全設定・思考量まで`GenerateOptions`から指定できるので、入口を増やさずに済みます。ただし`gemini.Schema` / `ThinkingLevel` / `SafetyThreshold`は`genai`の**型エイリアス**で、型を作り直してはいません。フィールド名のコンパイル時検査を捨てずに`import`だけを止める、意図的な折衷です。したがって効果は「別のSDKへただちに差し替わる」ことではなく、**手を入れる場所が上位の7リポジトリではなくこの1つに集まる**ことです。
* **リトライはSDKに任せる**: 以前は`netarmor/retry`で自前に包んでいましたが、genai SDKがHTTP層で408 / 429 / 5xxと通信エラーを判定する仕組みを持つため、そちらへ寄せました。**判定表を写すと、SDKが対象を増やしたときにこちらだけ古い一覧を持ち続けます**。実際、写していた表は408と502を取りこぼしていました。ポーリング系だけはリクエスト単位でリトライを打ち消します。内側でバックオフすると、呼び出し側の間隔とタイムアウトが意味を失うためです。
* **発射間隔と重複排除は`callguard`に集約**: レート制限・1回あたりの上限時間・同一内容の同時実行の重複排除は`callguard`パッケージが持ちます。以前は利用側の2キットに逐語コピーがあり、**片方のコメントが警告していた落とし穴に、もう片方がそのまま嵌っていました**。
* **構造化出力でも、デコード前に1段挟む**: `ResponseSchema`を渡しても、完結したJSONの後ろに余分な閉じ括弧や説明文が継ぎ足されて返ることがあります。`CleanJSONResponse`は文字列を削るのではなく、**`json.Decoder`に最初の1値だけをデコードさせて止めます**。末尾を正規表現で削る実装は、本文に`}`を含むJSON——歌詞や台本はまさにそれです——で壊れるためです。直せなかった場合は元の文字列を返し、失敗をデコード側のエラーとして表に出します。黙って握り潰さないためです。
* **用途別の最小インターフェース**: 生成のほかに`VideoGenerator`（`StartVideo` / `PollVideo`）、`FileManager`、`BackendInspector`があり、3つを束ねた`Model`も用意しています。ポーリング間隔やタイムアウトを`VideoGenerator`に含めないのは、それが呼ぶ側の方針であって実装を差し替える理由にならないためです。
* **Lyria / Veo のワークフロー**: `lyria`パッケージが歌詞生成 → 楽曲設計図の作成 → 音声生成の3段を統合し、`veo`パッケージが動画生成の実行とポーリングを担います。中間に立つ`MusicRecipe`はこのエコシステムの共通通貨で、**動画側のオーケストレーターも同じレシピを入力に取ります**。

[GitHub - shouni/go-gemini-client](https://github.com/shouni/go-gemini-client)

### gemini-image-kit

エコシステム内で画像を描くレイヤーは、すべてこのライブラリに集約されています。生成の入口は`ports.ImageGenerator`の`Generate(ctx, ImageRequest)`ひとつで、参照画像が0枚でも複数枚でも同じメソッドです。

* **参照画像の送り方はアプリが選ぶ**: `gs://`を転送せず直接参照する`GCSResolver`、取得してインライン送信する`FetchResolver`、File APIへ上げてキャッシュする`FileAPIResolver`を`ResolverChain`で並べます。**キットが黙って既定を選ばないのは、これが運用上の判断だから**です。`gs://`しか使わない構成なら、取得もキャッシュも注入せずに済みます。バックエンド制約に反する組み合わせ（Vertex AIにFile API経路など）は**構築時に**弾きます。生成は成功してしまうぶん、実行時まで気付けないと見つけにくいためです。
* **シードは自前で決めてから送る**: シード未指定でも生成側で決めてから送信するため、`ImageResponse.UsedSeed`は常に実際に使われた値を指します。**APIはレスポンスにシードを返さないので、これが無いと同じ絵を再現できません**。
* **MIMEは推測できなければ付けない**: URI参照なら拡張子から、インライン送信なら実データから判定します。PNGをJPEGと申告するような誤った型宣言を避けるためで、**分からないことを分からないまま渡します**。
* **転送と流量を内蔵で面倒みる**: PNG/GIFは必要な場合のみJPEGへ再エンコードし、不要なら`bufio.Reader`でストリームのまま流します。同一ソースへの同時アップロードは`singleflight`で1回に集約され、レート制限・並列度・タイムアウトもオプションで指定できます。利用側で`errgroup`と`rate.Limiter`を組む必要がありません。
* **外部URLの取得経路は注入で決める**: 外部URLからの取得は`ports.Downloader`経由に限定し、SSRF対策やドメイン制御はアプリケーション側で適用します。

参照解決の選び方、MIME推測、シードの扱いをコードまで降りて追ったのが「[Go言語で構築する堅牢なAI画像生成パイプライン：MIME推測・File APIキャッシュ・SSRF対策](https://zenn.dev/snknsk/articles/b694340e5cf15e)」です。

[GitHub - shouni/gemini-image-kit](https://github.com/shouni/gemini-image-kit)

### go-character-kit

キャラクターの`id` / `name` / `seed` / `reference_url` / `visual_cues` をJSON定義として読み込み、検証し、参照するだけの小さなライブラリです。

* **構築時に検証し、以後は読み取り専用**: 入力を複製して保持し、参照系APIもコピーを返します。生成の途中でキャラクター定義が書き換わる経路を作りません。Seedの差し替えも元の集合を書き換えず、派生を返します。
* **「見つからないとき」を型で決める**: ID未指定や未知のIDはデフォルトキャラクターへ倒します。呼び出し側にnilチェックと「代わりに誰を使うか」の判断を書かせないためです。
* **参照画像はアスペクト比で選ぶ**: 生成するコマの縦横比に合う参照URLを返します。同じキャラクターでも、比率が変われば渡すべき参照画像が変わるためです。

独立したライブラリにしている理由は、Seedと参照アセットという一貫性の核が**漫画と動画の両方に必要**だからです。どちらかのオーケストレーターに置けば、もう一方がそれをimportすることになります。現在は`go-comic-kit`・`go-veo-orchestrator`を含む5リポジトリが同じ定義を読んでいます。

[GitHub - shouni/go-character-kit](https://github.com/shouni/go-character-kit)

## 🎨 生成オーケストレーター (Generation Orchestrators)

AI抽象化層を組み合わせて「1つの作品」を組み立てる層です。何を作るかのドメイン（作品の状態・工程の順序・一貫性の維持）を持つのがここまでで、これより上のアプリケーションは受付・認証・非同期実行だけを担います。

### go-comic-kit

キャラクターの一貫性を保ったまま、漫画を工程単位で組み立てるツールキットです。

* **MangaState = 唯一の真実源**: 1作品の全状態（台本・登場キャラ・生成条件・成果物URL）を単一の状態ドキュメントとして永続化します。履歴一覧も詳細参照も、アプリ側はstateを読むだけで済みます。
* **冪等・工程単位の操作**: 章立て・章台本・デザインシート・パネル・ページの各操作が、いずれもstateを受け取って更新済みstateを返します。**「12パネル中3番だけ再生成」がAPIとして表現でき**、MCPツールと1対1で対応します。一括操作を別メソッドにしているのは、生成済みをスキップする判断をキット側に持たせるためです。途中で失敗しても、次の実行は残りだけを生成して再開できます。
* **3要素でキャラクターを固定する**: Seed値（基盤）・参照アセット（外見）・VisualCues（詳細）の3つで固定します。シードは明示指定が無くても「前回値 → 主役キャラのSeed → 新規採番」の順で必ず決まった値が送られ、`UsedSeed`から再現できます。
* **プロンプトはすべてアプリが持つ（DI必須）**: 工程ごとに5種あり、`workflow.Args`で**必ず注入します**。キットは内蔵プロンプトを持ちません。プロンプトは作品ごとに作り込む文言なので、キットに置くと1文字変えるたびにキットのリリースが必要になるためです。
* **重複排除は層が2つ要る**: 同一内容の同時実行は`singleflight`で1回にまとめられます（実装は`go-gemini-client`の`callguard`）。これは**プロセス内**に対する重複排除で、時間をまたいだ再配信を止めるのは`go-job-kit`の再実行ガードの役目です。層が違うので、両方が要ります。

MangaState と部分再生成の実装は「[Go言語で構築するAI漫画生成：状態ドキュメント1枚で「3コマ目だけ描き直す」を成立させる設計](https://zenn.dev/snknsk/articles/8896d7672c5f68)」で1本にしています。

[GitHub - shouni/go-comic-kit](https://github.com/shouni/go-comic-kit)

### go-veo-orchestrator

**Music Recipe（楽曲構成書）** から動画カット列を構造化し、Googleの動画生成AI **Veo** へ渡すバックエンドオーケストレーターです。

* **音の展開からタイムラインを組む**: レシピの`sections`や`cuts`から尺と開始・終了位置を補完し、`audio_cue`をVeo用プロンプトへ注入します。音楽の展開に同期したカット割りになります。
* **途中から再開できるカット連鎖**: 各カットが状態と`video_id`を保持し、生成済みはスキップして次カットへ引き継ぎます。引き継ぐ値は**`gs://`のURIでなければなりません**。Veoのオペレーション名は連鎖の入力にならないため、URIが得られなかった場合はあえて空のままにして、誤った値が次カットへ渡るのを防いでいます。
* **Veoへの通信をアダプタに閉じる**: 実通信は`ports.VideoRunner`という1メソッドの契約にだけ現れ、**実装はこのリポジトリに含まれません**（呼び出し側が注入します）。オーケストレーション・キーフレーム生成・メタデータ保存は、それぞれ別の関心として分かれています。

### go-review-kit

Gitの2つのリファレンス間の差分を取り、AIにレビューさせ、結果を公開して通知するまでを1本のパイプラインとして提供します。

* **AI SDKに依存しない**: このリポジトリ群では例外的に、**AIクライアントを一切同梱していません**。レビュアーは`Reviewer`（差分だけを見る単発）と`WorkspaceReviewer`（作業ディレクトリを調べるエージェント型）の2つのポートとして定義され、実装は利用側が差し込みます。どのSDKでレビューするかはアプリの選択であり、ライブラリが抱えると全利用者にその依存が伝播するためです。直接依存は`go-git`のみです。
* **差分の外を読ませるための追加能力**: 差分の取得はコミット同士のツリー比較なので、作業ツリーの中身はレビュー対象のリビジョンとは限りません。エージェント型を使う構成でのみ`WorkspaceProvider`を型アサーションで要求し、レビュー直前に明示的なチェックアウトを行います。
* **型付きのレビュー結果**: 出力は`Report`としてデコード・検証済みの状態で受け渡します。重大度と判定の列挙値は`review`パッケージだけが持ち、AI側の出力スキーマもそこから組み立てるため、両者が食い違いません。
* **差分なしは失敗ではない**: 差分が空なら`StatusSkipped`を返し、公開はせず通知だけを行います。保存・通知・後始末は呼び出し元の締め切りから切り離すため、**レビューがタイムアウトで打ち切られた直後でも失敗の記録と通知は届きます**。

ポートを2つに割ったことが実際に効いた場面は、利用側のアプリを扱った「[エージェントは「差分の外」を読む：ADK for Go で AI レビューを作り直した実践](https://zenn.dev/snknsk/articles/adk-go-agent-review-practice)」に書いています。

[GitHub - shouni/go-review-kit](https://github.com/shouni/go-review-kit)
